# Подготовка анализа защищённости через ЕЛК

После выделения ресурсов и настройки целевого окружения владелец подаёт заявку
через ЕЛК. До подачи собирается состав работающей установки и результаты проверок
того же выпуска. Состав checkout, успешная сборка и отсутствие находок сканера
сами по себе не подтверждают защищённость сервера.

## Состав и границы проверки

| Область | Что фиксировать и проверять |
|---|---|
| Python и приложения | Полные версии Python, Django, Gunicorn, Django Ninja, Jinja2, Pydantic и pydantic-core; остальные прямые и транзитивные зависимости API, web и оператора |
| Системные библиотеки | Пакеты итоговых образов, включая OpenSSL, PCRE2, expat, Connector/C и libc; пакеты и ядро целевой Ubuntu |
| Периметр | nginx или Caddy выбранного контура, подключённые модули, фактическая конфигурация TLS, HTTP, заголовков и лимитов |
| База данных | Версия работающей MariaDB или PostgreSQL, версия пакета с суффиксом дистрибутива, права прикладной роли, доступность порта и восстановление копии |
| Идентичность выпуска | SHA checkout, изменения файлов, label каждого контейнера, image ID и доступные registry digest; соответствие отчётов этому выпуску |
| Поддержка | Поддерживаемые ветки и сроки поддержки у поставщика; доступность официальных исправлений для используемой платформы |
| Применимость CVE | Точный пакет и диапазон версий, необходимые модули и настройки, достижимость через используемый протокол, влияние на приложение |

Рабочий web использует Django/Jinja2 и собственные браузерные модули. Vue и
`@vue/server-renderer` в этом checkout не используются. Строку из внешнего примера
нельзя переносить в состав приложения. Если компонент появится, проверяют конкретный
пакет, режим рендеринга и полный граф его зависимостей.

APT-версии учитываются целиком: Ubuntu может переносить исправление в пакет без
смены основной upstream-версии. Применимость сверяется с
[Ubuntu Security](https://ubuntu.com/security/cves), а не только сравнением цифр.
После обновления пакета проверяют перезапуск сервиса; установленный новый пакет
не доказывает, что работающий процесс уже использует его.

## Уточнения к письму от службы безопасности

Сведения ниже сверены 5 октября 2026 года. Перед выпуском источники проверяют снова.

| Компонент | Факт и решение |
|---|---|

| nginx | CVE-2026-42533 исправлена в 1.30.4, CVE-2026-90439 – в 1.30.5, CVE-2026-15176, CVE-2026-93479 и CVE-2026-97205 – в 1.30.6. Образ закреплён на 1.30.6 и digest. Проверяют фактический образ, PCRE2 и модули; отсутствие проблем с одной CVE не является заключением по всему nginx |
| Gunicorn | 26.2.0 опубликована в PyPI. Сайт релизов показывает 26.2.1/26.2.2, но официальный API PyPI и повторное разрешение зависимостей их не предоставили. Сохранена устанавливаемая 26.2.0; доступность исправлений после неё и применимость заявленных ошибок ASGI остаются открытым вопросом перед выпуском. Настройки запуска в коде: HTTP/1, h2c выключен, keepalive 0, доверенные forwarded IP отсутствуют, PROXY protocol выключен. Это сужает условия некоторых ошибок, но не закрывает все ошибки ASGI. | Pydantic | В lockfile закреплены 2.13.5 и совместимый pydantic-core 2.46.5. CVE-2024-3772 исправлена уже в 2.4.0 для ветки 2.x. Требование более новой версии связывают с отдельной CVE либо конкретным исправлением |
| Оценка риска | CVSS записывается с версией шкалы, автором оценки и вектором. Например, для CVE-2026-42533 у F5 указаны 9.2 по CVSS 4.0 и 8.1 по CVSS 3.1. Это нельзя смешивать в одной колонке без пояснения |

## Воспроизводимые отчёты

Из checkout выбранного выпуска с синхронизированными Python-окружениями:

```bash
bash scripts/checks/audit-dependencies.sh security-reports
```

Каталог должен быть новым. Команда сохраняет `source.json` с составом трёх lockfile,
прямыми зависимостями, стадиями Docker-сборки и хешами файлов, а также шесть отчётов
pip-audit: runtime и development для backend, frontend и scripts. Проверяются все
области даже при находке в одной из них. Ненулевой код означает находку либо сбой;
отсутствующий отчёт не считается успешной проверкой. Требования с hash экспортируются
из frozen lockfile; resolver не обновляет версии незаметно.

CI сохраняет отчёты Python и итоговых образов как артефакты с SHA в имени на семь
дней. Trivy сохраняет находки всех уровней. HIGH, CRITICAL и неизвестная критичность
останавливают задание; MEDIUM и LOW остаются видимыми для разбора. Новая находка
не скрывается исключением ради успешного CI. GitHub actions закреплены полными
commit SHA, образы инструментов – digest. Из отчётов образов удаляется конфигурация,
включая env и историю сборки. Проверки образов относятся к собранным в CI образам,
а не автоматически к контейнерам на сервере.

Исключение по применимости не удаляет исходную находку. Для GO-2026-5932
проверка сверяет image ID Trivy с Docker, извлекает из того же образа список
`go list -deps` сборки Caddy и требует отсутствия всех `golang.org/x/crypto/openpgp`
пакетов. Список, его hash, image ID и основание сохраняются в `Applicability`.
Несовпадение образа, отсутствие доказательства, новый advisory или новая версия
пакета блокируют проверку. Сборка также останавливается при появлении OpenPGP;
`govulncheck` независимо проверяет достижимые Go-вызовы.
Основание: [официальное предупреждение Go](https://pkg.go.dev/vuln/GO-2026-5932).

Утилита gosu в совместимом PostgreSQL-образе пересобирается с `golang.org/x/sys`
0.48.0. Бюллетень [CVE-2026-39824](https://pkg.go.dev/vuln/GO-2026-5024) касается
Windows и версий ниже 0.44.0; модуль обновлён и в Linux-образе, с проверкой версии
в собранном бинарном файле. Успешную пересборку и новый image ID подтверждает CI.

## Вопросы за пределами перечня компонентов

### SQL-инъекции

Отдельная проверка SQL охватывает PostgreSQL, MariaDB/Django ORM, ручные запросы
API, медиатеку, управление сотрудниками, выдачу SQL-прав, перенос базы, миграции
и команды обслуживания. Поиск мест выполнения и динамической сборки дополняется
проверкой того, откуда поступают значения и идентификаторы; одно отсутствие
`RawSQL` или успешный аудит зависимостей не доказывает защиту от инъекций.

- Значения, включая email, slug, поисковые строки, JSON и списки `_in`, передаются
  драйверу отдельно от SQL. Кавычки, SQL-комментарии, UNION и названия функций
  остаются данными; запрещать эти слова в обычном тексте пользователя не требуется.
- Таблицы и поля задаёт `DATA_COLUMNS`; общий слой PostgreSQL и MariaDB проверяет
  один разрешённый список даже при пустых данных, фильтрах и группировке. Служебные
  модели и их внутренние имена не разрешаются автоматически из реестра Django.
- Сортировка, проекция, группировка, агрегатные поля и операторы фильтра проходят
  проверку до открытия транзакции. `_connector`, `_negated`, произвольные Django
  lookup и вложенные непроверенные словари не передаются в `Q` или SQL.
- Пустой идентификатор записи не снимает условие `WHERE` у изменения и удаления.
  Отсутствие `id` проверяется через `is None`, а не его истинность. Тест сохраняет
  контрольную строку после попыток изменить и удалить запись с пустым UUID.
- Динамические запросы медиатеки используют фиксированный `MEDIA_FIELDS`.
  Операторские имена MariaDB проходят строгую проверку; пароли роли API – параметры
  драйвера. Перенос PostgreSQL применяет `sql.Identifier`; выдача прав PostgreSQL
  использует `%I` для имён и `%L` для значений. Эти пути доступны оператору,
  прикладная роль остаётся ограниченной.
- `backend/tests/python/test_sql_injection.py` проверяет отказ до обращения к БД,
  сохранение и точный поиск шести SQL-payload, чтение/изменение/удаление/агрегацию
  только целевой строки, публичность новости, административный поиск и вход.
  Сценарии с реальной БД выполняются отдельно для PostgreSQL и MariaDB в CI.

В просмотренных путях прямую SQL-инъекцию не подтвердили. Дополнительное изменение
устраняет различие в проверке таблиц между двумя реализациями и обеспечивает ранний
отказ. Перед выпуском проверяют реальные grants и тот же образ приложения;
результат исходного статического аудита не объявляется полным покрытием репозитория.

| Область | Что проверено в коде или добавлено | Что требуется на целевом контуре |
|---|---|---|
| Почта и восстановление пароля | Внешний SMTP требует TLS до AUTH/DATA; тест снимает STARTTLS и проверяет отсутствие отправки credentials и письма | Сертификат, доставка и одноразовые ссылки через согласованный SMTP |
| Одновременные операции | Аватар заменяется под SQL-блокировкой с повторной проверкой профиля; тесты параллельной загрузки и обезличивания | Повторить сценарии с фактической БД и хранилищем; проверить лимиты ресурсов |
| Недоверенная копия | До расшифровки проверяются размер и место; запись не превышает исходный размер, распаковка ограничена свободным местом; резерв 1 GiB | Проверить дисковые квоты, целостность offsite и полный restore. CBC/PBKDF2 остаётся прежним совместимым форматом без MAC; checksums внутри архива не заменяют независимую аутентификацию копии |
| Обход полномочий и чужие данные | Сервер сверяет status/роль/поколение JWT; full_admin отделён от editor; SQL-роль API не меняет роли и не читает CMS metadata | Проверить реальные grants, тестовые роли и отзыв доступа. Гостевая корзина, агрегированная аналитика редактора и публичные аватары – действующая продуктовая политика |
| SQL injection, XSS, SSRF и файлы | Параметризованный SQL, allowlist идентификаторов, Jinja escaping, ограничения исходящих адресов/DNS, nofollow и сигнатуры файлов | Пройти пользовательские и административные сценарии; CSP и ограничения должны сохраняться на периметре |
| Оплата и webhooks | Сумму и статус подтверждает независимый запрос провайдеру, заказ блокируется в транзакции; Telegram проверяет отдельный webhook secret | Проверить выбранный магазин, адрес отправителя за proxy, повторы и работу разрешённых каналов |
| Секреты и поставка | Runtime/operator env разделены; сборка исключает .env/.pem/.key и для data; отчёты не содержат конфигурации image | Проверить доступ к host/Docker, registry, CI и закрытым файлам; отсутствие ключей в истории проверяется отдельно |
| Журналы и персональные данные | HTTP журнал не получает query/body/headers/IP; Sentry отправляет фиксированные коды; аудит остаётся чувствительным и изменяемым | Согласовать доступ, сроки хранения, внешнюю передачу и независимое сохранение важных событий |
| Доступность и поддержка | Таймауты, размеры запросов, route limits, один API worker, проверка диска и поддерживаемых веток | Проверить нагрузку, RAM/CPU, диск и алерты. Вторая реплика требует общего rate limit и блокировок |
| Восстановление и инциденты | Отдельная новая БД и uploads, выключенные интеграции, сравнение таблиц/файлов, порядок отката | Подтвердить восстановление целевой копии, независимый доступ к ключу, offsite и доступность ответственного |

Статический аудит исходного выпуска 21765f6 подтвердил три проблемы: необязательный
STARTTLS, гонку замены аватара и отсутствие предварительного бюджета расшифровки.
Исправления выше проверяются регрессионными тестами. Исходный аудит частичный:
полностью прочитаны 230 из 564 файлов; остальные файлы и серверные настройки не
объявляются проверенными. Сканирование зависимостей, интеграционные тесты и
проверка сервером службы безопасности дополняют друг друга.

На целевой Ubuntu для нового MariaDB/nginx-контура, из `/opt/club`:

```bash
sudo install -d -m 0700 /root/club-security-assessment
sudo python3 scripts/diagnostics/security-inventory.py \
  --output /root/club-security-assessment/runtime.json \
  --host \
  --container api="$(sudo docker compose --env-file /etc/club/compose.env -f deploy/compose.mariadb.yml ps -q api)" \
  --container web="$(sudo docker compose --env-file /etc/club/compose.env -f deploy/compose.mariadb.yml ps -q web)" \
  --container nginx="$(sudo docker compose --env-file /etc/club/compose.env -f deploy/compose.mariadb.yml ps -q nginx)"
sudo sh -c 'umask 077; mariadb --batch --skip-column-names --execute "SELECT VERSION();" > /root/club-security-assessment/mariadb-server.txt'
```

`runtime.json` должен быть новым файлом. Скрипт требует Python 3.12+, не устанавливает
пакеты и не читает env, журналы, пользовательские данные или TLS-ключи. Собирает версии
и пакеты только указанных работающих контейнеров, image ID, label и registry digest,
а с `--host` – пакеты Ubuntu и ядро. Остановленный или недоступный контейнер даёт
частичный отчёт и ненулевой код. `assessment_performed=false` остаётся даже при полном
сборе состава: инвентаризация не выдает заключение о защищённости.

Отдельно сверяют пакеты контейнеров с lockfile и image ID с очищенными отчётами Trivy.
API и web должны соответствовать выбранному выпуску; метки разных SHA, отсутствующий
digest или несовпадение состава требуют разбора. Для прежнего контура используют
параметры его Compose и роли `caddy`/`postgres`. На Docker-хосте сохраняют также вывод
`docker version` и `docker compose version`, а версию работающей PostgreSQL запрашивают
через `SELECT version()` в уже разрешённом локальном сеансе. Не подставляют секреты в
аргументы или отчёт. Пакеты остановленного оператора проверяются по скану его образа.

## Проверка конфигурации и подготовка заявки

Перед подачей заявки проверяют на том же выпуске:

1. Извне доступны только согласованные входные порты; API и база закрыты.
2. TLS, редиректы, CSP, ограничения заголовков и тела, таймауты, rate limit и
   передача клиентского IP работают в выбранном nginx/Caddy-контуре.
3. Неверные и неоднозначные HTTP-запросы не обходят периметр. Проверены сочетания
   Content-Length/Transfer-Encoding, повторные заголовки и используемый worker Gunicorn.
4. Роли, SQL-параметры, экранирование шаблонов, загрузки и обращения к внешним
   сервисам проверены профильными тестами. Нет передачи пользовательского словаря
   напрямую в параметры ORM. Для ReDoS учитываются реальные входы и лимиты данных.
5. Сервисы после обновления перезапущены; восстановление копии и откат проверены
   в изолированной среде. Работающая база не заменяется автоматически.

В заявку включают согласованный адрес и контур, ответственного, точные версии,
SHA и image ID/digest, даты сканирования, очищенные отчёты и открытые вопросы.
Учётные записи для анализа, временные доступы и окно тестирования согласуются
отдельно. Закрытые файлы конфигурации, данные участников и секреты не прикладывают.

Для каждой находки ведут строку: пакет и фактическая версия; CVE/GHSA; источник и
дата; CVSS; диапазон; условия и доказательство применимости; исправление;
повторная проверка; остаточный риск и решение ответственного. Допустимые выводы:
«исправлена указанная CVE», «условия не выполняются, проверено», «требует проверки».
Формулировка «всё чисто» не заменяет анализ. Принятие остаточного риска выполняет
ответственный владелец совместно со службой безопасности.

Порядок обновления, резервирования и отката – в
[runbook](deploy-runbook.md) и [инструкции MariaDB](mariadb-migration.md).
