# Ресурсы и измерения

Замеры ниже сделаны на прежней схеме с PostgreSQL, Fastify и Caddy, до перехода на
MariaDB и nginx. Замеров на MariaDB в документе пока нет. Текущее устройство описано в
[architecture.md](../development/architecture.md).

Репетиция 29–30.09.2026 относится к локальному native-стенду. Первая установка
и нагрузка проверены на `12f07763243600499ae1e02ce84b9f601a523c98`, обновление
и повторный deploy – на `f649a3d2d248c1492e0feba79470edca829035a8`.
Версии источника и цели переноса указаны в разделе восстановления.
Команды установки, обновления и восстановления описаны в
[runbook](deploy-runbook.md), состояние проверок – в
[project-state.md](project-state.md).

## Что измерено

Ubuntu 24.04.4 ARM64 запущена в Lima/VZ на Mac. VM выделены 4 vCPU, 6 GiB RAM
и 20 GiB виртуального диска. Linux видит `MemTotal=6 197 366 784` байта
(5,772 GiB). Docker Engine 29.8.1, Compose 5.5.1 и Buildx 0.37.1 установлены
внутри VM; каталоги Mac в неё не смонтированы.

Работают PostgreSQL, Fastify, web, Caddy и тестовый Mailpit. API и PostgreSQL
не публикуют порты хоста. HTTPS доступен через loopback Caddy; клиент проверяет
сертификат по корню CA этого стенда. Внешняя почта, платежи, Telegram и фоновые
интеграции выключены. Сборка скачивает зависимости; её время включает сеть.

Перед нагрузочным замером в БД были один выпускник, одна заявка, одна программа
ДПО и одна новость с одним PNG. Товары и события не были наполнены. Три небольших
WAV импортированы **после** нагрузочного замера. Этот набор не представляет
объём рабочей базы или файлового архива.

| Свободный запас | Не менее большего из 20% диска и 5 GiB |

### Полные копии и временное место

Каждый snapshot содержит полный дамп БД и все uploads. `BACKUP_KEEP_DAYS=14`
задаёт срок хранения, а не предел числа файлов. При одной копии в сутки нужно
планировать около 14 полных ежедневных снимков; дополнительный deploy или ручная
копия увеличивают расход. На границе срока новый снимок появляется до удаления
старых. Offsite создаёт отдельную копию и не освобождает локальное место.

Для оценки обозначим:

- `DB` – размер БД из `pg_database_size()`;
- `U` – размер uploads;
- `P` – суммарный payload snapshot, записанный в `metadata.json`;
- `B_i` – фактический размер каждого сохраняемого зашифрованного снимка.

Тогда место под копии равно `Σ B_i`. Сжатие аудио заранее не закладывается:
уже сжатые MP3/M4A могут почти целиком повторяться в каждой полной копии.
Например, **при предположении** о 5 GiB таких файлов только 14 копий uploads
потребуют примерно 70 GiB, ещё до учёта БД, рабочего uploads и временных файлов.
Это пример расчёта, а не размер архива Клуба.

Встроенные проверки места требуют:

```text
backup:  free(BACKUP_DIR) ≥ 3 × (DB + U) + 256 MiB
restore: free(work) и free(DockerRootDir) ≥ 3 × (DB + U + P) + 256 MiB
```

Restore также сверяется с `restore_required_bytes` из metadata. Это защитные
оценки свободного места, не измеренные пики потребления. Для планирования
одновременного рабочего и проверочного контура отдельно учитывайте новые тома
БД/uploads и образы: restore сохраняет источник. Если копии и Docker находятся
на разных файловых системах, свободное место требуется на каждой.

Пусть `S` включает ОС, образы, кэш, рабочие данные, журналы и все копии, а `W`
– площадь для ближайшей операции и отдельного восстановленного контура. Для
диска `D` выбирайте:

```text
D ≥ S + W + max(0,20 × D, 5 GiB)
```

Preflight проверяет минимум 5 GiB свободного места. Его успешный результат
не заменяет расчёт хранения копий и данных на год.

### Рост за год

Сейчас нет подтверждённого прогноза числа участников, заявок и аудиовыпусков.
До выбора диска владелец задаёт предполагаемое число новых файлов в месяц,
их средний размер, удаление старых файлов и срок хранения копий. Для uploads:

```text
U_год = U_сейчас + 12 × (число_изображений_в_месяц × средний_размер_изображения
                        + число_аудио_в_месяц × средний_размер_аудио)
        − объём_планового_удаления_за_год
```

Рост БД оценивается отдельно по размеру строк, индексов и WAL на репрезентативном
тестовом наборе. Раз в месяц пересчитывайте фактический размер БД, uploads,
снимков и свободный запас. Порог монитора 85% занятого диска сигнализирует об
ухудшении ситуации; планировать постоянную работу у этого порога не следует.

## Выбор конфигурации

| Сценарий | Рекомендация и границы доказательства |
|---|---|
| Разработчик | Python 3.14 и uv; Docker для PostgreSQL и интеграционных проверок. Ресурсы всех локальных приложений учитываются на Mac отдельно. Для полной Ubuntu-репетиции используйте проверенные 4 vCPU/6 GiB и диск по расчёту выше |
| Изолированный QA | 4 vCPU/6 GiB – единственная проверенная VM-конфигурация. Исходные 20 GiB вместили первый стек, его сборку и маленький набор; дополнительные контуры и копии требуют нового расчёта свободного места |
| Публичный VPS | Для первой проверки сохраняйте 4 vCPU/6 GiB и один экземпляр API. Диск выбирайте по uploads и полным копиям. На целевом сервере отдельно проверяются его CPU, архитектура, I/O, внешняя сеть, TLS и рабочие интеграции |
| Сборка на сервере | Предусмотрите запас CPU и диска под старые/новые образы и кэш; холодная сборка этой VM занимала CPU до 99,82%. Выполняйте её в согласованное окно. Снижение CPU/RAM сначала проверяется отдельным полным прогоном |

4 vCPU/6 GiB – подтверждённый размер репетиции, а не доказанный аппаратный
минимум. Конфигурации с меньшей RAM и CPU не испытывались. Swap может дать
оператору время при кратком пике, но не заменяет RAM и влияет на задержки;
сборка и нагрузка со swap отдельно не проверены.

ARM64-замеры нельзя напрямую переносить на AMD64. CI проверяет сборку, сценарии
и зависимости, но не измеряет ресурсную ёмкость целевого VPS. Текущий deploy
собирает образы на сервере. Доставка готовых образов из registry потребует
отдельного пути выпуска и проверки отката.

Используйте одноразовый синтетический стенд. Пример команды внутри VM с Node
проекта и корнем CA текущего Caddy:

```bash
LOAD_SYNTHETIC=true LOAD_BASE_URL=https://localhost:9445 \
  HTTPS_CA_FILE=/etc/club/local-ca.crt \
  LOAD_DURATION_SECONDS=60 LOAD_REQUESTS_PER_SECOND=10 \
  LOAD_CONCURRENCY=4 LOAD_MAX_REQUESTS=600 \
  uv run --directory backend python ../scripts/diagnostics/measure-load.py > moderate-load.json
```

Параллельный сбор ресурсов запускайте с выбранным Compose-проектом и конечным
сроком, например:

```bash
LOAD_SYNTHETIC=true LOAD_COMPOSE_PROJECT=club-native-ubuntu \
  RESOURCE_DURATION_SECONDS=72 RESOURCE_INTERVAL_SECONDS=2 \
  python3 scripts/diagnostics/measure-resources.py > moderate-resources.jsonl
```

Храните JSON и логи вне Git. В доказательствах этой репетиции сохранены
`native-ubuntu-install-summary.json`, `native-ubuntu-disk-images.txt`,
`normal-load.json`, `moderate-load.json`, четыре окна ресурсных метрик и
`native-ubuntu-import.log`. Для обновления и копии сохранены
`native-ubuntu-update-summary.json`, `native-ubuntu-idempotent-summary.json`
и `native-ubuntu-snapshot-size.txt`; для restore –
`native-restore-exact-fixed.log`, `native-restore-exact-read.log` и
`native-restore-exact-import.log`. Перенос старой установки подтверждают
`native-restore-legacy.log`, `legacy-source-fingerprint.json`,
`legacy-restored-fingerprint.json`, `legacy-source-after-fingerprint.json`
и `legacy-native-login.log`; запуск служб – `native-systemd-fixed.log`.
Изменение наполнения БД, конфигурации, SHA или оборудования требует нового
замера с записанными условиями.
